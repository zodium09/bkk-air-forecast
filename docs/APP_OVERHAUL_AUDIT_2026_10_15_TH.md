# วิเคราะห์แอปเพื่อยกเครื่อง: เจ้าพระยา ฝน และสถานการณ์น้ำ

วันที่ตรวจ: 15 ตุลาคม 2569 (Asia/Bangkok) · ฐานโค้ด `7d8f8d51fc21226837e54aceb3ef2e52d29ff26e`

## 1. ข้อสรุปและโจทย์ที่ผู้ใช้ยืนยัน

ควรเปลี่ยนแกนผลิตภัณฑ์จากแอปสภาพอากาศก่อนออกจากบ้าน เป็น **เครื่องมือติดตามฝนและสถานการณ์น้ำทั้งระบบลุ่มเจ้าพระยา** จุดขายควรเป็นการเชื่อมหลักฐานที่กระจัดกระจายให้ตอบได้ว่า “เกิดอะไรที่ไหน เปลี่ยนอย่างไร เกี่ยวข้องกับลุ่มน้ำส่วนใด และควรติดตามหลักฐานอะไรต่อ”

ผู้ใช้ยืนยันในแชตนี้:

- ผู้ใช้หลัก: คนติดตามฝน น้ำท่วม และสถานการณ์ลุ่มน้ำ
- ขอบเขตยกเครื่อง: แนวคิดผลิตภัณฑ์ เนื้อหา UX/UI และระบบข้อมูล
- พื้นที่: ทั้งลุ่มเจ้าพระยา รวมปิง วัง ยม น่าน และป่าสัก โดยคงสะแกกรังที่มีอยู่แล้ว
- ประสบการณ์: สองโหมด คือ **สรุปทั่วไป** และ **ติดตามเชิงลึก**

สองโหมดต้องใช้แหล่งข้อมูล เกณฑ์ สถานะ และบริบทพื้นที่เดียวกัน ต่างกันที่ความละเอียดในการนำเสนอ ไม่ควรสร้างสองแอปที่คำนวณคนละชุด

ข้อเสนอสำคัญ: ยกเครื่องโครงสร้างการอ่านและฐานข้อมูลอย่างเป็นลำดับ เก็บตัวแปลงข้อมูลและกฎความถูกต้องเดิมที่ผ่านการทดสอบ ไม่เริ่มด้วยการเปลี่ยนสี เพิ่มกราฟ หรือเขียนระบบใหม่ทั้งหมดในคราวเดียว

แผนลงมือทำและข้อความส่งต่ออยู่ใน [SOL_OVERHAUL_HANDOFF_2026_10_15_TH.md](SOL_OVERHAUL_HANDOFF_2026_10_15_TH.md)

## 3. ของดีที่ต้องรักษา

1. **ความหมายของข้อมูลค่อนข้างรอบคอบ**: แยกค่าตรวจวัด พยากรณ์ น้ำทำนาย ข้อมูลเก่า และข้อมูลขาด มีหน่วยและแหล่งที่มา
2. **ไม่แต่งข้อมูลให้กราฟเต็ม**: มีการรักษา null/ศูนย์จริง/ระดับติดลบ เว้นเส้นเมื่อประวัติขาด ไม่เอาระดับน้ำต่าง datum มาลบกัน
3. **มีฐานเชื่อมแผนที่กับรายละเอียด**: เลือกจังหวัดและจุดน้ำแล้วเปิดสถานีเดียวกันได้ พื้นที่สิงห์บุรียังคงอยู่เมื่อไปหน้าฝนหลังเริ่มต้นหน้าเสร็จ
4. **มีองค์ประกอบเข้าถึงได้อยู่แล้ว**: ภาษาไทย, skip link บางหน้า, ป้าย controls, กราฟที่ใช้คีย์บอร์ดได้บางชุด, ตารางประกอบ, reduced motion และการพัก animation
5. **มีโครงสร้างรองรับความล้มเหลว**: timeout, สถานะ live/degraded/unavailable, การเก็บค่ารอบก่อนพร้อมเวลา, หยุด refresh เมื่อซ่อนแท็บ และ tests ด้านข้อมูลจำนวนมาก

### กฎภาษาและสถานะ

ใช้คำ 4 กลุ่มที่เห็นแยกกันเสมอ: **ตรวจวัด**, **พยากรณ์**, **ประกาศหน่วยงาน**, **สรุปโดยแอป**. “ข้อมูลจำลอง” อยู่เฉพาะพื้นที่ทดลอง

เปลี่ยน copy ตัวอย่าง:

| เดิม/ลักษณะที่พบ | ข้อเสนอ |
|---|---|
| น้ำมาก / ถึงตลิ่ง · 5 | น้ำมากตามเกณฑ์ต้นทาง 5 สถานี · ถึง/เกินตลิ่ง 0 สถานี |
| ข้อมูลล่าสุดหรือเกณฑ์ยังไม่พร้อม (ถนนนอก กทม.) | ยังไม่มีข้อมูลจุดตรวจวัดถนนสำหรับพื้นที่นี้ · ชุดนี้ครอบคลุม กทม. |
| เปิดการแจ้งเตือน | ติดตามการเปลี่ยนแปลงขณะเปิดหน้านี้ |
| สรุปตามเวลาปัจจุบัน เมื่อเลือกวันอื่น | พยากรณ์วันที่ [วัน] · ค่าตรวจวัดยังใช้เวลาล่าสุดของสถานี |
| โอกาสเกิดฝนในช่วงใดช่วงหนึ่งของวัน | โอกาสฝนรายชั่วโมงสูงสุดของวันที่เลือก |
| ไม่มีเหตุ/ปกติ เมื่อข้อมูลไม่มี | ยังสรุปสถานการณ์ไม่ได้ · มีข้อมูลล่าสุด [n]/[N] สถานี |

ไม่ควรแทนถ้อยคำซับซ้อนด้วยคำเตือนยาวทุก panel: ข้อมูลที่จำเป็นต้องอยู่ข้างค่า ได้แก่ ชนิดข้อมูล หน่วย เวลา พื้นที่ สถานะ; วิธีคำนวณยาวย้ายไป disclosure ที่เปิดได้จากตรงนั้น

## 6. UX/UI ที่เสนอ

### สรุปทั่วไป

- Header ขนาดกะทัดรัด: ชื่อผลิตภัณฑ์, เลือกลุ่มน้ำ/พื้นที่, โหมด, เวลาอ้างอิง
- จอแรก: บทสรุป 1–3 ประเด็นที่มีหลักฐาน + สถานะความพร้อมข้อมูล + ปุ่มเปิดเชิงลึก
- จากนั้นแผนที่ภาพรวมหนึ่งชุด, การเปลี่ยนแปลงสำคัญ, สถานีที่ติดตาม และประกาศที่เกี่ยวข้อง
- หากไม่มีประเด็นเข้าเกณฑ์ ให้สรุปความครบของข้อมูลและเสนอจุดที่ติดตามได้ ไม่แสดงความสงบแทนข้อมูลขาด
- ไม่มีภาพ hero ขนาดใหญ่บนหน้าติดตามประจำ; คำอธิบายเริ่มใช้เป็นส่วนเล็กที่ปิดได้และไม่บังคับ

### ติดตามเชิงลึก

- Desktop: ตัวเลือกพื้นที่/ชั้นข้อมูลด้านข้าง, แผนที่ตรงกลาง, panel สถานี/เหตุที่เลือกด้านขวา, กราฟและตารางด้านล่าง
- Mobile: สลับ **แผนที่ / รายการ / กราฟ** ในบริบทเดียวกัน; detail ใช้แผงย่อขยายที่เข้าถึงด้วยคีย์บอร์ดหรือหน้า station จริง ไม่ซ้อน modal หลายชั้น
- เลือกเวลาแล้วแยกตำแหน่ง “ขณะนี้” กับ cursor ที่เลือก; ข้อมูลอนาคตไม่ทับเวลา observations
- เปรียบเทียบสถานีได้ 2–4 จุดตามทางน้ำ ใช้ small multiples เมื่อ datum หรือขนาดต่างกัน; ไม่เอาระดับ รทก. คนละพื้นที่มาจัดอันดับความรุนแรงโดยตรง
- มีลิงก์แชร์ที่คืนพื้นที่ สถานี ชั้นข้อมูล โหมด และช่วงเวลาได้; ปุ่มกลับล่าสุดเห็นชัด

### ภาษาภาพ

- ฉากใช้งาน: คนอ่านไทยบนโทรศัพท์กลางวันและผู้ติดตามบนจอทำงาน ต้องมองตัวเลข/เวลาเร็ว; light เป็นค่าเริ่มต้นและคง dark mode ที่อ่านได้นาน
- ใช้ฟอนต์ไทยหลักหนึ่งตระกูลที่ทดสอบแล้ว; body 16 px, metadata 13–14 px, หัวข้อ 20–28 px, ตัวเลขสำคัญ 28–36 px เป็นค่าเริ่มต้นเพื่อทดสอบ
- ใช้สีน้ำเงิน/เขียวอมฟ้าเป็น identity แบบพอดี; สีสถานะต้องมีข้อความ/สัญลักษณ์ ไม่ใช้เต็มการ์ดทุกใบ
- ปริมาณฝนใช้สเกลต่อเนื่อง, สถานะเฝ้าติดตามใช้ชุดสีแยก, missing ใช้ลาย/ข้อความ; ทุก legend ระบุหน่วยและเกณฑ์
- ลดการ์ดซ้อน เปลี่ยนค่ารายสถานีเป็นแถวเปรียบเทียบ ใช้กรอบเฉพาะสิ่งที่เลือก/มีปฏิสัมพันธ์
- ทุกกราฟมี metric, unit, timezone, data class, missing state และตาราง; tooltip ไม่เป็นทางเดียวในการอ่านค่า
- animation ใช้บอกการเลือกหรือข้อมูลเปลี่ยน ไม่ทำให้น้ำดูไหลแรงขึ้นโดยไม่มีข้อมูลแนวโน้ม

### การเข้าถึง

เป้าหมาย WCAG 2.2 AA และ usability จริง: focus ชัด, ไม่ถูก sticky bar บัง, contrast ข้อความทั่วไป ≥4.5:1, ข้อความใหญ่ ≥3:1, สีไม่เป็นช่องทางเดียว, รองรับ 200% text zoom และ reflow 320 CSS px. ตั้งเป้าปุ่มหลัก 44×44 px; เกณฑ์ AA เรื่อง target size ขั้นต่ำคือ 24×24 CSS px พร้อมข้อยกเว้นด้าน spacing ตาม W3C ไม่ควรกล่าวว่า 44 px เป็นขั้นต่ำ AA ทั้งหมด

รอบนี้พบ controls บางชิ้นมีมิติต่ำกว่า 24 px จากการสำรวจ DOM แต่ยังไม่ได้วิเคราะห์ข้อยกเว้น spacing ทีละชิ้น จึงจัดเป็นรายการตรวจ ไม่ใช่ข้อสรุปว่าไม่ผ่านทั้งหมด

## 7. ระบบข้อมูลและการเดินระบบ

**เรื่องที่สำคัญที่สุดคือข้อมูลทั้งลุ่มน้ำและประวัติที่ตรวจสอบย้อนกลับได้**

- ทำ catalog แยก basin, sub-basin, river reach, province, station และ agency/source IDs ไม่ใช้จังหวัดแทนลุ่มน้ำ
- ตรวจความเชื่อมโยง upstream/downstream จากข้อมูลภูมิศาสตร์และ metadata ที่ตรวจสอบได้; ถ้ายังไม่ทราบให้แสดง unknown ไม่สร้างความสัมพันธ์จากระยะใกล้อย่างเดียว
- เก็บ raw payload หรือหลักฐานอ้างอิงตามสิทธิ์การใช้, checksum, source timestamp, ingestion timestamp, model issue time และ valid period เป็นคนละช่อง
- แยก snapshot ปัจจุบันกับ time series; เก็บ revision เมื่อแหล่งแก้ค่าเดิม กำหนด canonical observation ต่อ key โดยไม่ทิ้งร่องรอย
- คุณภาพข้อมูลต้องแยก freshness, coverage, datum, completeness, provider availability และ assessment eligibility ไม่ยุบเป็นสีเขียว/แดงเพียงช่องเดียว
- งานเก็บต่อเนื่องต้องอยู่ฝั่ง server และไม่ต้องอาศัยคนเปิดหน้า; มี heartbeat, last success, lag, duplicate rate และ failure reason
- เลือก runtime หลักและ durable database ให้แน่นอนก่อนย้ายข้อมูล: repo มีทั้ง Next/Vercel config และ Cloudflare/D1 worker แต่รอบนี้ยังไม่ได้ตรวจ deployment จริง
- local `.data` ใช้สำหรับพัฒนาได้ แต่ไม่ใช้เป็นหลักฐานว่าประวัติ production คงอยู่; ต้องทดสอบ restart/redeploy/หลาย instance และ restore
- ไม่สร้างคะแนนความเสี่ยงน้ำท่วมรวมใหม่จนมีนิยาม หลักฐาน validation และผู้รับผิดชอบเกณฑ์; เริ่มจากสัญญาณที่อธิบายได้แยกเรื่อง
- การแจ้งเตือนภายนอกเป็นระยะหลัง มี opt-in, deduplication, cooldown, expiry/retraction และผลทดสอบ false alert; ปุ่มในหน้าปัจจุบันต้องไม่สัญญาว่าทำงานเมื่อปิดหน้า

## 8. ด้านอื่นที่ควรอยู่ในแผน

| ด้าน | งานที่ควรทำ |
|---|---|
| Performance | เก็บ baseline บน production build; โหลดข้อมูลสำคัญก่อน; จำกัด map instance; shared query/cache; ไม่เรียก provider ใหม่ตามทุก pointer move |
| Security | ตรวจ server-only credentials, validation/range limits, SSRF allowlist ถ้ามี proxy, rate limits ของ endpoint แพง; mutation ของระบบเฝ้าระวังต้อง auth/authorization/CSRF ตามสถาปัตยกรรม |
| Privacy | อย่าบันทึกตำแหน่งจริงลง URL/analytics โดยปริยาย; share public station/area ID; ชี้แจง third-party map/embed และใช้สถานที่ด้วยการกระทำของผู้ใช้ |
| SEO/Sharing | metadata แยกหน้า/ลุ่มน้ำ/สถานี, canonical URL, OG ที่บอกพื้นที่และชนิดข้อมูล; หน้า demo noindex; ไม่ทำ share image ที่ดูเหมือนข้อมูลสดตลอดไป |
| Observability | API สำเร็จแต่ข้อมูลหมดอายุต้องตรวจพบได้; metrics ต่อ source/basin; เกณฑ์ alarm ของ collector และรายการ gaps |
| Analytics | วัดเวลาไปถึงข้อมูลที่ต้องการ, การเปิดหลักฐาน, flow map→station→history, switch mode และการกลับมาติดตาม; ไม่เก็บ precise location |
| Content operations | ทุก metric/rule มีเจ้าของ นิยาม source reference วันที่ทบทวน; มี annual rollover สำหรับ tide; runbook เมื่อแหล่งหยุด/เปลี่ยน schema |
| Maintainability | แยก shell/query/state/formatting/domain; ใช้ shared context serialization; ไม่แทรก business rules ใน JSX; รวบรวมเอกสารที่ซ้ำ |
| การขยายบริการ | คง public read-only ก่อน; ยังไม่มีหลักฐานว่าต้องมีบัญชีหรือระบบชำระเงินเพื่อแก้โจทย์นี้; เพิ่มเมื่อมี use case ที่จำเป็น |

## 9. เกณฑ์ความสำเร็จที่เสนอ

เป็นเป้าหมายสำหรับทดสอบหลังทำ ไม่ใช่ผลที่แอปปัจจุบันผ่านแล้ว:

- ผู้ใช้ใหม่ 4 ใน 5 คนระบุพื้นที่ ชนิดข้อมูล และเวลาที่กำลังอ่านได้ถูกต้องภายใน 30 วินาที
- ผู้ใช้ 4 ใน 5 คนแยก “สถานีน้ำสูง”, “รายงานน้ำท่วมจริง” และ “ยังไม่มีข้อมูล” ได้จากหน้าสรุป
- เลือกลุ่มน้ำ → สถานี → กราฟย้อนหลัง ใช้ไม่เกิน 3 การกระทำหลัก โดยไม่สูญเสียบริบท
- หน้าแรก 390×844 และ 1280×720 เห็นพื้นที่ เวลา และสรุปที่มีหลักฐานหรือสถานะข้อมูลไม่พร้อมในจอแรก
- โหมดสองแบบให้ค่าตรงกันเมื่อ context ตรงกัน และ deep link คืน context ได้
- ทุกลุ่มน้ำที่ประกาศรองรับมีรายการแหล่ง/สถานี/coverage และสถานะจริง ไม่จำเป็นต้องมีข้อมูลทุกชนิดครบ แต่ต้องไม่แสดงว่าครบเมื่อไม่มี
- production build ตั้งเป้า LCP ≤2.5 s, INP ≤200 ms, CLS ≤0.1 ที่ p75 เมื่อมี field data เพียงพอ; ก่อนนั้นใช้ lab test เป็น proxy และรายงานข้อจำกัด
- ไม่อนุมัติการเปลี่ยนความหมาย metric, สีเกณฑ์, ความสด หรือ datum จาก visual review อย่างเดียว ต้องมี semantic tests

## 10. แหล่งอ้างอิงภายนอก

- [ThaiWater](https://www.thaiwater.net/?lang=th) และ [ภาพรวมบริการ ThaiWater](https://www.thaiwater.net/mobile): ใช้อ้างอิงขอบเขตบริการที่เชื่อมข้อมูลฝน น้ำ และเขื่อน ไม่ได้ยืนยันว่าทุกชุดมี public API หรือสิทธิ์นำกลับเผยแพร่ครบ
- [มาตราน้ำ 2569 กรมอุทกศาสตร์](https://hydro.navy.mi.th/waterlaveltable): มีตารางอ้างอิงทั้ง Lowest Low Water และ Mean Sea Level ต้องเลือก datum ให้ถูก
- [Open-Meteo Weather API](https://open-meteo.com/en/docs): ใช้ตรวจนิยามตัวแปร ช่วงเวลาฝน และ provenance ก่อนทำ content contract
- [WCAG 2.2](https://www.w3.org/TR/WCAG22/) และ [Target Size Minimum](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum): ฐานเกณฑ์ accessibility

แหล่งใหม่เกี่ยวกับประกาศ ผลกระทบน้ำท่วม อัตราการไหล ประตูน้ำ และการระบายต้องผ่านการสำรวจ endpoint สิทธิ์ ความถี่ และคุณภาพในงานระยะฐานข้อมูลก่อนสัญญาฟีเจอร์
