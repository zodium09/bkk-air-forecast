## 1. ข้อเสนอหลัก

ปรับขอบเขตวันที่8กันยายน2026: รวมการหาแหล่งย้อนหลัง การเชื่อมต่อ/จัดเก็บ และแผน14sessions โดยรายละเอียดอยู่ใน [แผนฐานข้อมูลย้อนหลัง การเชื่อมต่อ และรายละเอียด 14 sessions](D:/MyWebApps/bkkair/docs/HISTORICAL_DATA_CONNECTION_SESSION_PLAN_TH.md)


ต่อยอดแอพปัจจุบันให้มี 3 มุมมองที่ใช้ข้อมูลและตัวเลือกชุดเดียวกัน:

1. **แผนที่** — ดูว่าพื้นที่ไหนมีแนวโน้มอย่างไร เลือกสถานที่และเวลา
2. **วิเคราะห์** — ดูกราฟขนาดอ่านได้ เปรียบเทียบช่วงเวลาและสถานที่ และตรวจข้อมูลที่รองรับข้อสรุป
3. **รายงาน** — สรุปข้อมูลที่เลือกเป็นเอกสารที่อ่านต่อเนื่อง พิมพ์/บันทึก PDF และส่งออกตารางได้

ยืมวิธีเล่าเรื่องและการจัดองค์ประกอบจาก LPHO Dengue ได้แก่ สรุปประเด็นสำคัญ กราฟพร้อมคำอธิบาย การเปรียบเทียบพื้นที่ และรายงานแยกจากหน้าปฏิบัติงาน แล้วเปลี่ยนให้เหมาะกับพยากรณ์ PM2.5 ฝน และความร้อน

**แนวทางภาพ:** คงเอกลักษณ์ navy / teal / blue / amber ของ BKK Air ใช้พื้นที่ว่างและลำดับตัวอักษรเพิ่มความอ่านง่าย ให้กราฟเป็นส่วนหลักของหน้าวิเคราะห์ และให้หน้ารายงานมีรูปแบบเอกสารชัดเจน

**สิ่งที่ส่งมอบในรอบวางแผนนี้:** บทวิเคราะห์อ้างอิงจริง แผนหน้าจอและกราฟ สัญญาข้อมูลที่ต้องเพิ่ม ลำดับพัฒนา และเกณฑ์รับงาน ไม่ใช่ dashboard ไข้เลือดออก และไม่ใช่การเริ่มปรับโค้ดแอพอากาศแล้ว

### สิ่งที่ควรปรับเมื่อยืมรูปแบบ

1. **ลดข้อมูลซ้ำเหนือกราฟ:** reference มี KPI สองแถวและซ้ำในหัวรายงาน ทำให้กราฟเริ่มค่อนข้างล่าง หน้าวิเคราะห์ใหม่ใช้ KPI เพียงหนึ่งแถว และรายงานไม่แสดงแถว KPI ของหน้า dashboard ซ้ำอีกชุด
2. **ขยายตัวอักษร:** CSS ของ reference มี labels ประมาณ 8.5–12.5 px หลายส่วน ตั้งเป้า labels ที่ใช้ตัดสินใจ 14 px ขึ้นไป เนื้อหา 16 px และตัวเลขหลักประมาณ 28–40 px ตามพื้นที่
3. **ลดจำนวนเมนูระดับแรก:** reference มีเมนูหลายรายการ แอพอากาศควรจัดตามกิจกรรมผู้ใช้สามแบบ แล้วเปลี่ยนหัวข้ออากาศผ่านตัวเลือกเดิม
4. **ลดสีเตือนที่ไม่สื่อสถานะ:** ใช้สีหมวดข้อมูลสม่ำเสมอ แสดงสถานะคุณภาพกับระดับค่าคนละระบบ ไม่ทำทุกการ์ดให้เหมือนประกาศเตือน
5. **ผูกข้อความกับข้อมูลจริง:** source ของรายงานอ้างอิงมีทั้งค่าคำนวณและข้อความ/ตัวเลขกำหนดตายตัว บางแผงใน snapshot ของเว็บจริงแสดงบริบทเวลาหรือค่าที่ไม่ตรงกัน จึงต้องให้รายงาน BKK Air ใช้ selector และ snapshot ชุดเดียวกับกราฟ
6. **แยกหน้าพิมพ์ให้เฉพาะรายงาน:** CSS print ของ reference เปิดทุก .tab-panel การออกแบบใหม่ต้องพิมพ์เฉพาะ report root พร้อม legend และ source ในหน้าที่เกี่ยวข้อง
7. **ไม่ย้ายเนื้อหาเชิงองค์กรที่ไม่เกี่ยวกับงาน:** SWOT, ระบบบริการสุขภาพ, operational disease KPI และสูตร Farrington/EWMA ไม่ใช่องค์ประกอบเริ่มต้นของรายงานพยากรณ์อากาศ

### ประเด็นที่ต้องแก้หรือยืนยันก่อนนำตัวเลขขึ้นรายงาน

- Probability axis ปัจจุบันคำนวณ ceiling จากค่าสูงสุดของข้อมูล ควรคง 0–100% เพื่อเทียบข้ามช่วงได้
- X ticks ของกราฟ 3 ชั่วโมงแสดงชื่อวันเป็นหลัก ควรระบุชั่วโมงและการแบ่งวัน
- ข้อความบางจุดใช้ “7 วัน” ตายตัว แต่ provider บางแบบมี horizon สั้นกว่า ต้องคำนวณจากช่วงข้อมูลจริง
- การเทียบกับวันถัดไปใน LocationInsight อาจเริ่มจากช่วง 3 ชั่วโมงแล้วเทียบ daily summary ต้องกำหนดคู่เปรียบเทียบที่ aggregation และ cadence ตรงกัน
- ภาพรวม MapWorkspace เป็นค่าเฉลี่ยจุดที่มีข้อมูล ส่วนการรวมข้อมูลบางระดับของ heat ใช้นิยามการเฉลี่ยอีกชั้น ต้องระบุนิยามกลางก่อนทำรายงาน
- fetchedAt, observedAt และ model initialization เป็นคนละเวลา บาง payload ไม่ระบุเวลาเริ่ม model run ต้องแสดง “ไม่ระบุ” ตามจริง
- ความพร้อมของ TMD ต้องดู actual provider/fallback ใน payload ไม่อนุมานจากปุ่มตัวเลือก

## 5. โครงสร้างประสบการณ์ที่เสนอ

### 5.1 การนำทาง

คงหน้าแรกและเส้นทาง air/rain/heat เป็นแผนที่ เพิ่มตัวสลับมุมมองใกล้หัว workspace:

**แผนที่ | วิเคราะห์ | รายงาน**

ข้อเสนอเชิง implementation ที่ให้เริ่มทำ: ใช้ view state ของ shared workspace เช่น query view=analysis / view=report เป็นระยะแรก ให้แผนที่ยังคงตัวตนเดิมใน SPA session และหยุด animation/งาน render ที่ไม่จำเป็นเมื่อซ่อน หากภายหลังต้องแยก route ให้ใช้ selection store และ selectors ชุดเดิม

- Map → Analysis: ส่ง layer, metric, source, province/location, data mode, valid time/cadence และช่วงข้อมูลที่มี
- Analysis → Map: กลับไปตำแหน่ง/เวลาที่เลือกไว้ คง scroll/focus ตามทางเข้าที่ชัดเจน
- Analysis → Report: เตรียม snapshot จาก context และข้อมูลที่แสดงจริง
- Report → Analysis: กลับมุมมองวิเคราะห์ปัจจุบัน; ถ้ามีข้อมูลใหม่ ให้ผู้ใช้เห็นว่ารายงานเดิมเป็น snapshot ก่อนหน้า
- เปิด URL เดิม: คืนตัวกรองได้ แต่ข้อมูลที่โหลดใหม่อาจเป็นคนละรอบกับครั้งก่อน ต้องไม่สื่อว่าเป็นรายงานย้อนหลังที่ตรึงไว้
- เปิด view=report โดยไม่มี snapshot: แสดงหน้าตั้งค่าหรือเตรียมรายงานจากตัวกรองนั้นก่อน พร้อมแจ้งว่าจะใช้ข้อมูลที่โหลดขณะนี้ ไม่สร้างภาพว่ามีรายงานเดิมที่บันทึกแล้ว

### 5.3 มุมมองสรุปรวมหลายหัวข้อ

ใช้หัวข้อ PM2.5 / ฝน / ความร้อนเรียงเป็นกราฟแยกแถวที่แชร์แกนเวลา ป้ายแต่ละแถวมีหน่วยและแหล่งข้อมูลของตัวเอง

- หากเลือกภาพรวม 7 วัน แต่ TMD ให้เพียง 2 วัน ให้เว้นช่วงที่เหลือพร้อมป้าย coverage
- เลือก daily เพื่อดูข้ามหัวข้อก่อน เพราะ PM2.5 ไม่มีข้อมูล 3 ชั่วโมงตามสัญญาปัจจุบัน
- โหมด 3 ชั่วโมงแสดงเฉพาะหัวข้อที่มี ไม่เติมค่าฝุ่นรายวันซ้ำให้ดูเหมือนพยากรณ์รายชั่วโมง
- ไม่ใช้กราฟสามแกน Y หรือเอาทุกตัวแปรมารวมเป็นเส้นเดียว
- ไม่สร้างคะแนนความเสี่ยงสิ่งแวดล้อมรวมจากการ normalize ตัวเลขต่างหน่วยโดยไม่มีวิธีที่ตกลงไว้

### 6.1 Anatomies ของกราฟทุกชนิด

1. ชื่อ metric ที่คนเข้าใจ + หน่วย
2. พื้นที่/สถานที่และชนิดข้อมูล
3. ช่วงเวลาที่ใช้จริงและ cadence
4. Plot และสเกลที่เหมาะกับข้อมูล
5. Legend ที่คลิกซ่อน/แสดงเส้นเปรียบเทียบได้เมื่อมีมากกว่าหนึ่ง series; primary series ยังแสดงเสมอ
6. Tooltip/รายละเอียดที่ใช้คีย์บอร์ดและสัมผัสได้
7. คำสรุปสั้นจากข้อมูลจริง พร้อมลิงก์ไปช่วงเวลาที่อ้าง
8. Source/fallback, freshness และ coverage ที่มีผลต่อการตีความ

Tooltip ขั้นต่ำ: สถานที่ · วันและเวลา ICT · ค่าและหน่วย · aggregation · พยากรณ์/ตรวจวัด/IDW · actual provider · เวลาข้อมูลที่มี

**กติกา legend ระยะแรก:** ซ่อนเฉพาะเส้นเปรียบเทียบ ไม่เปลี่ยนชุดข้อมูลวิเคราะห์หรือ KPI โดยอัตโนมัติ KPI ระบุ primary series ที่อ้างอิง รายงานเก็บ primarySeriesId และ visibleSeriesIds ของกราฟ ส่วนตาราง/CSV ยังครอบคลุมสถานที่ที่เลือกทั้งหมดและระบุขอบเขตนี้ชัดเจน

### 6.2 กติกาภาพกราฟ

- PM2.5/ฝนที่เป็นค่าบวกไม่ใช้ smoothing ที่สร้างค่าติดลบหรือยอดที่ไม่มีในข้อมูล
- Probability ใช้ domain 0–100%; rainfall bars เริ่มที่ 0
- กราฟเปรียบเทียบตัวแปรเดียวกันต้องใช้ domain ร่วมภายในชุด
- Heat/temperature สามารถใช้แกนไม่เริ่ม 0 เพื่ออ่านความเปลี่ยนแปลง แต่แสดง ticks/ช่วงแกนชัด และไม่ใช้พื้นที่ทึบหลอกว่าเป็นปริมาณสะสม
- หากใช้ risk bands ให้ใช้เกณฑ์ที่มีในแอพและตรวจช่วงเฉลี่ย/metric ว่าเข้ากันก่อน ไม่เพิ่มเลขเกณฑ์ใหม่ในงาน visual redesign
- สีความเสี่ยงกับสีบอก provider/series ต้องไม่ทำหน้าที่ทับกัน เส้นเปรียบเทียบใช้ทั้งสี รูปแบบเส้น และ label
- Confidence band แสดงเมื่อมี quantiles/ensemble หรือวิธีคำนวณที่ตรวจสอบได้จริง ไม่ใช้ reliability heuristic หรือค่าประมาณทั่วไปสร้างช่วง “ความเชื่อมั่น 95%”
- “ค่าต่ำสุด–สูงสุดของจุดในพื้นที่” เป็น spatial spread ไม่ใช่ forecast uncertainty ต้องเรียกตามความหมายจริงหากเพิ่ม
- Daily labels แสดงวัน/วันที่; 3-hour labels แสดงชั่วโมงและเส้นแบ่งวัน; ไม่ให้วันและชั่วโมงสับสน

### 6.3 ชุด KPI ของหน้าวิเคราะห์

ใช้ 4 การ์ดที่นิยามชัด:

| การ์ด | นิยาม | ตัวอย่างป้าย |
|---|---|---|
| ค่าช่วงที่เลือก | ค่า ณ source point/IDW หรือค่าเฉลี่ยจุดที่ผ่านเกณฑ์ของ scope ที่เลือก | “โอกาสฝน · ช่วง 12:00–15:00” |
| ค่าสูงสุดตามเวลา | ค่าสูงสุดของ series เดียวกันในช่วงที่เลือก พร้อมเวลาที่เกิด | “สูงสุดในช่วงที่มีข้อมูล · วันที่…” |
| เปลี่ยนจากเวลา A | ค่า B − A เมื่อ metric/provider/aggregation/cadence จับคู่ได้ | “เพิ่ม 20 จุดเปอร์เซ็นต์จากเวลา A” |
| ความครบถ้วน | จำนวนค่าที่ใช้ได้/จำนวนค่าที่คาดหวังในช่วงที่ร้องขอ และสถานะคุณภาพ | “มีข้อมูล 5/7 วัน · 8/9 จุดในวันที่เลือก” |

แยก “สูงสุดตามเวลาในพื้นที่ที่เลือก” ออกจาก “จุดที่มีค่าสูงสุด ณ เวลาที่เลือก” ให้เป็นคนละชื่อ/กราฟ ไม่ใช้คำว่า “สูงสุด” ที่ไม่บอกว่าข้ามเวลา หรือข้ามสถานที่

เมื่อไม่มี denominator ที่ตรวจสอบได้ แสดงจำนวนค่าที่มีและช่วงที่มีจริง แทนการประดิษฐ์เปอร์เซ็นต์ความครบถ้วน

## 7. การโต้ตอบที่ต้องเชื่อมกัน

| การกระทำ | สิ่งที่เปลี่ยน | สิ่งที่ต้องคงไว้ |
|---|---|---|
| เปลี่ยนจังหวัด | series, KPI, จุด/แผนที่, heatmap, ตาราง | metric/source/cadence ถ้ายังรองรับ |
| เปลี่ยน metric ฝน % ↔ mm | ชนิดกราฟ แกน หน่วย legend คำสรุป cache/request | พื้นที่และวันที่ที่ยังมี |
| Hover จุดกราฟ | preview/tooltip เท่านั้น | selected time และแผนที่ |
| Click/tap/Enter จุดกราฟ | selected time, map, inspector, KPI | พื้นที่/provider |
| ตรึงเวลา A | แสดง marker A และค่าผลต่าง A→B | B เปลี่ยนต่อได้ |
| เปลี่ยน cadence | series และคู่เวลาใหม่ที่เข้ากัน | ใช้ date/time ที่ใกล้เคียงตามกติกาเดิม ไม่จับ raw index ข้าม cadence |
| คลิก heatmap | เลือกตำแหน่ง/ขอบเขตและเวลาเดียวกับ cell | แหล่งข้อมูลและ metric |
| คลิกอันดับจุด | inspector และกราฟของจุดนั้น | เวลาที่เลือก |
| เปลี่ยน source | โหลด/เลือก dataset identity ใหม่; แจ้ง fallback จริง | พื้นที่เดิม; เวลา A ที่หมดช่วงต้องล้างพร้อมเหตุผล |
| เตรียมรายงาน | สร้าง snapshot จากข้อมูลที่กำลังแสดง | ไม่ให้ auto-refresh เปลี่ยนเลขในรายงานที่เตรียมแล้ว |

การเทียบ 2–3 ตำแหน่งในระยะแรกใช้ metric, actual provider, aggregation และช่วงเวลาที่เทียบกันได้ ไม่รวม data mode แบบตรวจวัดกับ IDW เงียบ ๆ หากขาดข้อมูลของตำแหน่งหนึ่ง ให้เว้นค่า ณ เวลานั้นโดยคง timestamp ของตำแหน่งอื่น ไม่เลื่อนข้อมูลมาจับคู่ตามลำดับ array

โหมดเทียบผู้ให้บริการหลายโมเดลเป็น feature แยกในระยะต่อไป ต้องใช้ valid interval เดียวกันและแสดง run time ที่ต่างกันตามจริง

**การตรวจเวลา A ใหม่:** เมื่อเปลี่ยน source, metric, cadence หรือพื้นที่ ต้องตรวจ compare key กับบริบทและช่วงเวลาชุดใหม่ทุกครั้ง เก็บ A ได้เมื่อค่าฐานกับค่าที่เลือกยังจับคู่ตาม metric/หน่วย/aggregation/ช่วงสะสมได้ หากไม่เข้ากันให้ล้างพร้อมเหตุผล โดยเฉพาะการสลับฝน % กับ mm ห้ามคงค่าฐานคนละตัวแปรมาคำนวณผลต่าง

### สถานะหน้าจอที่ต้องออกแบบ

- **Loading:** มีโครงคงความสูง ไม่กระโดด; ยังคงชื่อ context ที่ร้องขอ; ไม่แสดงค่าจาก provider เดิมด้วยชื่อ provider ใหม่
- **Empty:** “ไม่มีข้อมูลในช่วงที่เลือก” และทางกลับไปช่วงที่มีจริง
- **Partial:** แสดงส่วนที่มีพร้อมช่องว่างและ coverage
- **Fallback/degraded:** ใช้ข้อมูลได้แต่แสดง actual provider และสาเหตุที่สัมพันธ์กับกราฟ
- **Unavailable:** ไม่มีตัวเลขคาดการณ์แทนด้วย 0 ไม่มีพื้นผิว IDW ที่ดูเหมือนปกติ
- **Stale:** แสดงเวลาชุดข้อมูลเก่าและปุ่มลองโหลดใหม่; แยกอายุการ fetch กับอายุ observations
- **Selection expired:** ตำแหน่งหรือเวลา A ไม่อยู่ในชุดใหม่ บอกเหตุผลและคืน selection ที่รองรับอย่างชัดเจน

## 8. รูปแบบหน้ารายงาน

### 8.1 รายงานสองระดับ

**รายงานย่อ:** ค่าเริ่มต้นสำหรับใช้งานทั่วไป สรุปบริบท ประเด็นสำคัญ กราฟหลัก และที่มาข้อมูล เป้าหมายประมาณ 1–2 หน้า A4 ตามเนื้อหาจริง ไม่บีบตัวอักษรเพื่อบังคับจำนวนหน้า

**รายงานรายละเอียด:** เพิ่มตารางเปรียบเทียบสถานที่/ช่วงเวลา heatmap และภาคผนวกข้อมูล อาจหลายหน้า มี repeat table headers และเลขหน้าเมื่อเครื่องมือพิมพ์รองรับ

เริ่มจากรายงานหัวข้อที่เลือกเพียงหัวข้อเดียวให้ครบก่อน แล้วขยายเป็นรายงานรวม air/rain/heat โดยโหลดแต่ละ dataset เท่าที่จำเป็นและใช้ timestamp/provenance ต่อหัวข้อ

### 8.2 โครงรายงานย่อ

    รายงานแนวโน้มฝน — [พื้นที่]

    02 แนวโน้ม

ไม่มีคำสรุปเชิงเหตุและผลอัตโนมัติจากการเห็นเส้นกราฟสัมพันธ์กัน เช่น “ฝนทำให้ฝุ่นลด” เว้นแต่มีการวิเคราะห์ที่รองรับ งานระยะแรกบรรยายสิ่งที่ข้อมูลแสดงได้โดยตรง

### 8.3 ตัวอย่างข้อความแบบ template

ตัวอย่างต่อไปนี้เป็นแบบข้อความ ไม่ใช่ข้อมูลพยากรณ์จริง:

> ในช่วง [วันที่เริ่ม–วันที่สิ้นสุด] ค่า [metric] ของ [ขอบเขต] สูงสุดในช่วงที่มีข้อมูลที่ [เวลา] เท่ากับ [ค่า หน่วย] โดยใช้ [aggregation และชนิดข้อมูล] ข้อมูลครอบคลุม [จำนวนช่วงที่ใช้ได้/ช่วงที่ร้องขอ] และมาจาก [actual provider]

ถ้าไม่มีช่วงเปรียบเทียบที่เข้ากัน ให้ตัดประโยคเปรียบเทียบออกแทนเติมข้อความทั่วไป
ถ้าหลายช่วงค่าสูงสุดเท่ากัน ให้ระบุหลายช่วง/ช่วงแรกพร้อมจำนวนครั้งตาม rule ที่กำหนด
ถ้า coverage เปลี่ยนระหว่างวัน ให้แจ้งใกล้ประโยคแนวโน้ม

### 8.4 ความสวยงามของรายงาน

- หัวรายงาน navy หรือแถบสีหมวดข้อมูล บทสรุปเด่นด้วย hierarchy มากกว่าการใช้สีเตือนทุกคำ
- กราฟหลักเต็มความกว้างหน้าที่อ่านได้ ไม่ใช้ภาพ screenshot ของทั้ง dashboard ย่อใส่กระดาษ
- หน่วย legend และ source อยู่ในกราฟ/figure เดียวกัน ไม่ต้อง hover จึงอ่านได้
- พื้นขาวสำหรับ print มีขอบกระดาษและช่องไฟสม่ำเสมอ
- ตารางตัวเลขชิดขวา ใช้ tabular numerals และหน่วยที่หัวคอลัมน์
- ชื่อพื้นที่ไทยไม่ถูกตัดจนแยกพื้นที่ไม่ได้
- ปิด navigation, map controls, live animation และปุ่มต่าง ๆ เฉพาะใน print output
- ไม่บังคับใส่รูปเมืองหรือภาพตกแต่งในรายงาน; สงวนพื้นที่ให้ข้อมูล
- แผนที่ประกอบเป็นตัวเลือกหลังตรวจการ capture และ attribution แล้ว หาก capture ภาพ tiles ไม่สำเร็จ ให้ใช้ขอบเขต/จุดจากภูมิศาสตร์ที่ตรวจสอบแล้วหรือข้อความระบุขอบเขต ไม่พิมพ์กรอบแผนที่ว่าง

### 8.5 Snapshot และการส่งออก

- เมื่อกด “เตรียมรายงาน” สร้างค่าคัดลอกของข้อมูล context และผลสรุปเป็น snapshot ที่ใช้กับทุกองค์ประกอบ
- ปุ่มเตรียมรายงานไม่พร้อมใช้งานขณะ dataset ยังโหลดหรือไม่ตรง request/context ล่าสุด ตรวจ identity อีกครั้งขณะสร้าง snapshot หาก settled เป็น unavailable สามารถจัดรายงานสถานะข้อมูลได้โดยไม่มีค่าพยากรณ์เก่าหรือเลข 0 แทน
- รายงานใช้วันที่เต็มและ timezone หรือ formatter ที่รับวันอ้างอิงจาก generatedAt ที่ตรึงไว้ ไม่เรียก relativeDay() โดยอิงวันปัจจุบัน เพื่อให้ข้อความและวันที่ในรายงานเดิมไม่เปลี่ยนหลังเที่ยงคืน ICT
- การพิมพ์ คัดลอกข้อความ และ CSV อ่านจาก snapshot นี้ ห้ามดึง API ใหม่แยกกัน
- หากมีข้อมูลสดใหม่หลังจากนั้น แสดง “มีข้อมูลชุดใหม่” พร้อมให้สร้างรายงานใหม่ โดยรายงานเดิมยังคงค่าเดิม
- Snapshot ระยะแรกอยู่ใน session/browser memory; refresh หรือเปิดลิงก์อีกครั้งไม่ได้รับประกันเลขชุดเดิม
- ลิงก์ตัวกรองคือ “เปิดมุมมองนี้” ไม่ใช่ “ลิงก์รายงานที่บันทึกถาวร”
- ถ้าผู้ใช้ต้องการเก็บ/แชร์รายงานเดิมถาวร ต้องเพิ่ม storage, snapshot ID, version และ retention เป็นงานอีกระยะ
- CSV ใช้ UTF-8 ที่อ่านภาษาไทยได้ ระบุหน่วย เวลา ช่วงสะสม ตัวกรอง data mode แหล่งจริง aggregation และ quality; no-data เป็นค่าว่าง/สถานะ ไม่เป็น 0
- ส่งออกเฉพาะข้อมูลที่เลือก/ตารางใน snapshot และบอก scope บนปุ่มหรือคำอธิบาย
- ถ้ามีชื่อจากผู้ใช้/แหล่งภายนอก ต้อง escape CSV และป้องกัน spreadsheet formula interpretation ที่ขึ้นต้นด้วยอักขระสูตร

## 9. สัญญาข้อมูลและวิธีคำนวณที่ต้องกำหนดก่อนลงมือ

### 9.1 ข้อมูลต่อ series

| กลุ่ม | field ที่เสนอ | วิธีใช้ |
|---|---|---|
| ตัวแปร | metricId, unit, temporalAggregation, spatialAggregation, aggregationOrder | แยก rainProbability/rainAccumulation/temperatureMax/heatIndexMax/pm25DailyMean; เก็บการรวมเวลา พื้นที่ และลำดับ; ไม่อาศัย primary/secondary อย่างเดียวในรายงาน |
| ขอบเขต | scopeType, provinceId หรือ sourcePointId/coordinate | แยก point / observation station / IDW coordinate / sample-point mean |
| เวลา | validStart, validEnd, cadence, timezone | อ้างช่วงที่ค่ามีผลจริง ไม่ใช้เวลาสร้างหน้าเว็บแทน |
| ที่มา | requestedProvider, actualProvider, product/model, provenanceSegments หรือ source ต่อค่า | เปิดเผย fallback ระดับ metric/ช่วงเวลา/จุดเท่าที่ทราบ รองรับ mixed/unknown; ไม่ใช้ชื่อ model รวมแทนที่มาของทุกค่า |
| เวลาแหล่งข้อมูล | fetchedAt, observedAt, modelRunAt | แยกความหมาย; null หากต้นทางไม่ระบุ |
| คุณภาพ | status, reasons, validCount, expectedCount | tooltip, summary, report และการป้องกัน comparison ที่ไม่รองรับ |
| ค่า | timestamp/interval + value หรือ null | จับคู่ด้วยเวลา/ช่วง ไม่จับด้วย array index |
| การตรึงรายงาน | generatedAt, localSnapshotId, schemaVersion | ระบุ snapshot ใน session; ไม่อ้าง persistence จนมีจริง |

คง schema เดิมของ map เท่าที่ทำได้ เพิ่ม typed analysis adapter แทนการขยาย MapWorkspace ให้รับหน้าที่ของรายงานทั้งหมด

**กรณีแหล่งข้อมูลผสมที่ต้องรองรับ:** ใน app/lib/tmd-nwp-provider.ts ส่วน mergeTmdRainForecast เปลี่ยนข้อมูลปริมาณฝน แต่ precipitation_probability ยังมีที่มาจาก Open-Meteo ได้ การเลือก TMD จึงไม่ได้แปลว่าทุก metric/ช่วงเวลามาจาก TMD ให้เก็บ provenance segments ตามข้อมูลที่มี หากยืนยันแหล่งรายค่าไม่ได้ ใช้ “ผสม” หรือ “ไม่ระบุ” แทนการอนุมานจากชื่อ model รวม

### 9.2 นิยามกลางสำหรับภาพรวมพื้นที่

ข้อเสนอระยะแรก: ใช้นิยามเดียวกับภาพรวมที่แผนที่แสดงอยู่ คือ **ค่าเฉลี่ยของจุดข้อมูลที่ใช้ได้ในพื้นที่ที่เลือก** และทำให้ทุกหน้ารับผลจาก selector กลางเดียวกัน

- ชื่อบนจอควรเป็น “ค่าเฉลี่ยจุดข้อมูลที่มี” พร้อม n
- ไม่เรียกค่าเฉลี่ยประชากรหรือค่าเฉลี่ยถ่วงน้ำหนักทั้งจังหวัด
- ใช้เฉพาะ finite values ที่ผ่านเงื่อนไขคุณภาพและ scope
- ระบุลำดับการรวมให้ตรงกับตัวแปร: ภาพรวม probability/heat ที่นำ point maxima มาเฉลี่ยคือ mean ของ maxima รายจุด ไม่ใช่ max ของค่าเฉลี่ยพื้นที่ ป้ายอาจเป็น “เฉลี่ยค่าสูงสุดรายจุดในวันที่เลือก”; กรณี probability ไม่ใช่โอกาสฝนที่ใดก็ได้ในจังหวัด
- เก็บ valid count แยกในแต่ละช่วงเวลา หากจำนวนจุดเปลี่ยนต้องแสดงได้
- ไม่แก้สูตรการรวมของ API ทั้งระบบพร้อม redesign; analysis adapter ต้องระบุชัดว่ากำลังแสดง point mean หรือ source-defined regional statistic
- rainMeanMm, rainMaxMm และ rainWatchMm เป็นสถิติคนละชนิด เลือกชื่อให้ตรง ไม่สลับใช้โดยถือว่าเป็นค่าสูงสุดเดียวกัน
- การจัดกลุ่มรายจังหวัดต้องมี province ID จาก metadata/ขอบเขตที่ตรวจสอบได้ ไม่อนุมานจากการตัดข้อความชื่อจุด
- หากยังจัดกลุ่มพื้นที่ไม่ได้อย่างน่าเชื่อถือ ให้เริ่มอันดับ/เปรียบเทียบ source points ก่อน และปิดการจัดอันดับจังหวัดที่ยังคำนวณไม่ได้

### 9.3 กติกาเปรียบเทียบและรวมเวลา

- ค่าฝุ่นเฉลี่ยรายวันเปรียบเทียบกับค่าฝุ่นเฉลี่ยรายวัน ไม่เทียบ instant observation แล้วสรุป model error
- ฝนสะสมต้องเปรียบเทียบช่วงสะสมที่ยาวเท่ากันและไม่ทับกันเมื่อรวมยอด
- daily source ที่นิยามเวลาไม่ชัด ไม่สมมติว่า 00:00–24:00 ICT; แสดงตามข้อมูลที่มี และงดการรวมที่ต้องอาศัยนิยามนี้จนยืนยันได้
- Probability difference ใช้ percentage points; 60% → 80% คือ +20 จุดเปอร์เซ็นต์
- ไม่บวก % ฝนข้ามช่วง ไม่เฉลี่ยข้ามวันแล้วเรียกว่าโอกาสฝนตลอดสัปดาห์
- daily temperature maximum กับ 3-hour maximum เปรียบเทียบแยกบริบท
- ตัวหารศูนย์หรือฐานเปรียบเทียบหายไปคืน null/“เทียบไม่ได้” ไม่ผลิต Infinity/NaN หรือคำว่าเพิ่มไม่จำกัด
- สถานที่ A/B ที่มีเวลาหรือ provider ต่างกันต้องเปิดเผย และไม่สร้าง delta อัตโนมัติหากเทียบอย่างมีความหมายไม่ได้

### 10.1 หน้าที่ที่ควรแยก

| ส่วน | หน้าที่ | ข้อจำกัด |
|---|---|---|
| AnalysisContext | เก็บตัวเลือก/บริบทที่สอดคล้องกับ map URL | ไม่เก็บข้อมูล API ซ้ำ |
| Metric definitions | ชื่อ หน่วย รูปกราฟ aggregation และ comparison rule | ไม่ฝัง provider assumptions ที่ไม่อยู่ใน payload |
| Pure selectors | สร้าง series/KPI/table/comparison จาก inputs เดียวกัน | ไม่ fetch, ไม่ใช้เวลาปัจจุบันแบบแอบแฝง |
| Chart frame + renderers | ใช้กรอบแกน legend tooltip ร่วมกัน; renderer line/bar/heatmap | ไม่คำนวณความหมายข้อมูลคนละสูตรในแต่ละ renderer |
| Report builder | คัดลอก context/data และสร้าง summary/narrative | ไม่มีข้อความตัวเลขกำหนดตายตัว |
| Report view/print | นำ snapshot มาจัดเป็นเอกสาร | ไม่ subscribe live refresh ของ dashboard |
| Export formatter | serialize snapshot เป็น CSV/ข้อความ | ไม่เรียก API อีกชุด |

ใช้ custom SVG เดิมต่อในระยะแรก เพราะข้อมูล 7 วัน/ช่วง 3 ชั่วโมงและจุดเปรียบเทียบไม่มาก ประเมิน library ใหม่เมื่อข้อกำหนดที่ตกลงไว้ เช่น brush/zoom series จำนวนมาก เกินกว่าที่ renderer เดิมดูแลได้จริง และมีหลักฐานเรื่องประสิทธิภาพ/การเข้าถึงก่อนเพิ่ม dependency

- ลำดับ: บริบท → สรุปตัวกรอง/ปุ่มปรับ → KPI → กราฟ → ประเด็น → เปรียบเทียบ → ตาราง

- Touch tooltip/pinned detail ใช้ได้โดยไม่ hover
- ถ้าซ่อน filters ใน panel ต้องมีข้อความสรุปตัวเลือกปัจจุบันอยู่ข้างนอก

### Accessibility

## 12. ลำดับพัฒนาและจุดตรวจรับ

ปรับตามคำขอวันที่8กันยายน2026 ให้ฐานข้อมูลย้อนหลัง การเชื่อมต่อ และคลังพยากรณ์แต่ละรอบอยู่ในขอบเขตหลัก อ่าน [แผนฐานข้อมูลย้อนหลัง การเชื่อมต่อ และรายละเอียด 14 sessions](D:/MyWebApps/bkkair/docs/HISTORICAL_DATA_CONNECTION_SESSION_PLAN_TH.md) สำหรับแหล่งข้อมูล ผล probe schema ingestion และคำสั่งเริ่มแต่ละ session

| Session | งานหลัก | ผลส่งมอบ / เกณฑ์ผ่าน |
|---|---|---|
| S01 | ยืนยันแหล่งข้อมูลและ runtime | registry มีสถานะ verified/probed/pending และตัดสิน local/Cloudflare ตามหลักฐาน |
| S02 | พิสูจน์การเชื่อมต่อและ field mapping | mapping พร้อมตัวอย่างสำเร็จ/ผิดพลาด; ยังไม่รับรอง coverage ทั้งประเทศ/ทุกปี |
| S03 | ออกแบบ schema และ storage | นำเข้าซ้ำไม่เพิ่มข้อมูลซ้ำ; เก็บ revision และกู้คืน batch ได้ |
| S04 | เริ่มคลังพยากรณ์แต่ละรอบ | สอง capture แยกชัดและ replay ได้; ไม่ใช้เวลารับข้อมูลแทนเวลาออกรอบ |
| S05 | นำร่องอากาศย้อนหลัง | ตรวจวันข้ามเดือน/ช่วงฝน/หน่วย/coverage; รายงาน bytes และเวลาที่ใช้จริง |
| S06 | นำร่อง PM2.5 สถานี | ทุกสถานีที่แสดงมีที่มา/ขอบเขตยืนยัน; daily ไม่ถูกแปลงเป็น observed hourly |
| S07 | นำเข้าย้อนหลังเป็นช่วง | มี checkpoint/coverage ledger; หยุดและ resume ได้ ไม่มีการอ้างปีที่ยังไม่ได้อ่าน |
| S08 | เชื่อม API และ selectors | API/table/KPI เห็นช่วงข้อมูลและตัวเลขตรงกัน; missing ไม่เป็นศูนย์ |
| S09 | แดชบอร์ดฝนและมุมมองย้อนหลัง | คลิก/คีย์บอร์ด/มือถือผ่าน; downsampling รักษาผลรวมฝนและช่วงขาด |
| S10 | PM2.5 ความร้อน และพื้นที่ | ไม่เฉลี่ยสถานีเท่ากับค่าเฉลี่ยพื้นที่โดยไร้นิยาม; HI aggregation ถูกต้อง |
| S11 | ประเมินพยากรณ์ | ไม่รั่วข้อมูลอนาคต; แยกเทียบสถานีกับ reanalysis; ตัวอย่างไม่พอแสดงว่าไม่พอ |
| S12 | รายงานสามประเภท | เปิดค้าง/refresh ไม่เปลี่ยนรายงานเดิม; metadata และ coverage อยู่ในเอกสาร |
| S13 | ตรวจระบบและต้นทุน | ผ่าน critical cases, มี recovery runbook และขอบเขตค่าใช้จ่ายที่วัดจาก pilot |
| S14 | นำขึ้นใช้และส่งมอบ | มีเจ้าของงาน/บันทึกการรัน/alert ที่ดำเนินการได้ และหยุด collector ได้ |

ทุก session ยังเป็นแผน implementation; ผลอ่าน API/CSV ขนาดเล็กทำแล้วและบันทึกในเอกสารประกอบ ไม่ถือว่าฐานย้อนหลังพร้อมใช้งาน production หนึ่ง session มีขอบเขตและจุดตรวจรับ ไม่ใช่เวลารันตายตัว งาน backfill แบ่งตาม source/เดือนพร้อม cursor

หลัง S03 แบ่ง agent adapter อากาศกับ PM2.5 ได้ และให้ agent UI ใช้ contract/fixtures เดียวกันโดยมีเจ้าของ shared schema/selectors คนเดียว S04 เริ่มเก็บพยากรณ์แต่ต้น; S08–S09 เริ่มจาก pilot ได้ก่อน backfill ทุกปีครบ; S11 ที่ยังมีคู่ประเมินไม่พอไม่บล็อกรายงานย้อนหลังประเภทอื่น

## 13. เกณฑ์รับงานที่จับต้องได้

### ข้อมูลและการคำนวณ

1. Context เดียวกันให้ค่า KPI, tooltip, table, narrative และ CSV เท่ากันตาม precision ที่ระบุ
2. โอกาสฝน 60 → 80 แสดง +20 จุดเปอร์เซ็นต์ ไม่ใช่ +20% ของฐานเดิม
3. PM2.5 daily ไม่มีค่าหรือช่วง 3 ชั่วโมงที่สร้างซ้ำ
4. TMD daily ไม่เปิดช่อง 3 ชั่วโมงเมื่อไม่มีใน payload; horizon แสดงตามจริง
5. Daily rainfall และ 3h rainfall ไม่ถูกนับซ้ำในผลรวม
6. ค่า 0 แสดง 0; null/NaN/unavailable แสดง missing ตามกติกา และกราฟไม่เชื่อมช่วงขาด
7. จุด IDW ที่ไม่มี spatial support ไม่ได้ค่าเฉลี่ยของทั้งจังหวัดมาแทน
8. ผลต่างเวลา A/B คำนวณเฉพาะช่วงสะสมและ aggregation ที่ตรงกัน
9. ภาพรวมมีจำนวนจุดที่ใช้และชื่อวิธีเฉลี่ย ไม่มี label ที่สื่อ area/population weighting โดยไม่ได้ทำ
10. ค่า coverage ต้องใช้ denominator ที่มีหลักฐาน; unavailable ไม่ถูกตีความว่ามีสภาพอากาศปกติ
11. actual fallback/source แสดงตรงตามชุดข้อมูล แม้ requested provider ต่างออกไป
12. ไม่ใช้ fetchedAt เป็น model run time และไม่เติม modelRunAt เอง

### UX และกราฟ

13. Hover ไม่เปลี่ยนเวลา map; click/tap/keyboard เปลี่ยนค่า map/chart/inspector ไปบริบทเดียวกัน
14. Probability axis 0–100 และ rainfall bar เริ่ม 0
15. กราฟ 3 ชั่วโมงอ่านวันและชั่วโมงได้ ไม่เป็นชื่อวันซ้ำโดยไม่มีเวลา
16. เปลี่ยน metric แล้ว title/unit/legend/KPI/tooltip/export เปลี่ยนตามครบ
17. สถานที่ขาดข้อมูลไม่ทำให้ timestamps ของกราฟเปรียบเทียบเลื่อนมาชนกัน
18. กราฟมีตาราง/ข้อความประกอบที่ใช้ได้ด้วยคีย์บอร์ด
19. ไม่มี horizontal page overflow ที่ 320 × 667 และ 390 × 844; table/heatmap ที่เลื่อนมีขอบเขตชัด
20. ตรวจ tablet, 1280 × 720 และ 1440 × 1000 พร้อม 200% text zoom, light/dark และ reduced motion
21. สลับ Map → Analysis → Map คงตำแหน่ง/เวลา/สถานะแผนที่ตามข้อตกลง
22. Playback หรือการลากแผนที่ไม่ทำให้รายงานหรือกราฟเปรียบเทียบคำนวณหนักทุกเฟรม

### รายงาน

23. เตรียมรายงานแล้ว background refresh ไม่เปลี่ยนตัวเลขใน snapshot
24. Copy text/CSV/print อ่าน snapshot เดียวกัน ไม่เกิด fetch แยกและไม่ใช้ข้อความตัวเลขตายตัว
25. พิมพ์เฉพาะ report root; ไม่พิมพ์ sidebar/แผนที่สด/ทุก tab พร้อมกัน
26. Legend, unit, scope และ source ไม่หลุดจากรูปกราฟกลางหน้า
27. Header ตารางซ้ำในหน้าต่อ ข้อความไทยไม่ทับกัน ไม่มีแถวหรือกราฟตัดจนอ่านไม่ได้
28. รายงาน missing/fallback ยังอ่านสถานะและข้อจำกัดได้ชัดบนกระดาษ
29. CSV ภาษาไทย/ตัวคั่น/ค่าว่างและ formula escaping ถูกต้อง
30. เปิด URL ตัวกรองใหม่ไม่อ้างว่าเรียก snapshot ถาวรได้เมื่อยังไม่มี storage
31. ชุดฝนที่ผสมแหล่งข้อมูลแสดง probability/ปริมาณฝนตาม provenance จริง และใช้ mixed/unknown เมื่อระบุรายช่วง/รายจุดไม่ได้
32. Mean ของ point maxima ไม่ถูกเปลี่ยนเป็น max ของ spatial mean โดยไม่เปลี่ยนนิยามและ label
33. รายงานเดิมมีทั้งวันที่ ข้อความสรุป และตัวเลขเหมือนเดิมเมื่อเปิดค้างข้ามเที่ยงคืน ICT
34. เปลี่ยน provider แล้วกดเตรียมรายงานทันทีต้องไม่สร้าง snapshot จาก dataset เก่าติด metadata ใหม่
35. เปิด view=report โดยไม่มี snapshot แสดงขั้นเตรียมข้อมูลอย่างถูกต้อง; loading ไม่ส่งออกค่าค้าง และ unavailable สร้างได้เฉพาะรายงานสถานะที่ไม่มีค่าพยากรณ์แทน
36. สลับ metric/cadence/พื้นที่แล้วตรวจเวลา A ใหม่; legend ซ่อนเส้นเปรียบเทียบไม่เปลี่ยน primary KPI หรือตาราง/CSV เงียบ ๆ

### การทดสอบที่ควรเพิ่มเมื่อพัฒนา

ต่อยอด suites ที่มีอยู่ เช่น tests/unit/dashboard-controls.test.mjs, map-intelligence.test.mjs, map-surface.test.mjs, rain-communication.test.mjs, heat-forecast.test.mjs, api-failures.test.mjs และ tests/rendered-html.test.mjs

## 15. สิ่งที่ยังไม่รวมในรอบ redesign แรก

- สร้างโมเดลพยากรณ์ใหม่ เปลี่ยนสูตร IDW/bias correction หรือปรับเกณฑ์ความเสี่ยงโดยไม่มีโจทย์เพิ่ม
- เอา Farrington/EWMA/epidemic thresholds มาตั้งระบบเตือนอากาศ
- สร้าง baseline 5 ปี, YoY หรือ forecast accuracy จากข้อมูลพยากรณ์รอบปัจจุบัน
- สร้าง confidence interval จาก reliability heuristic
- สร้างระบบบัญชีผู้ใช้ จัดเก็บรายงานถาวร หรือส่งรายงานอัตโนมัติ
- สร้างคะแนนสุขภาพ/ความเสี่ยงรวม หรือคำแนะนำทางการแพทย์อัตโนมัติ
- เปลี่ยนแผนที่ให้ดูละเอียดกว่าแหล่งข้อมูลจริง หรือแสดง animation ตกแต่งว่าเป็น radar
- คัดลอกเนื้อหา โลโก้ หรือ identity ของเว็บโรคมาเป็นแบรนด์แอพอากาศ

## 17. จุดเริ่มต้นที่แนะนำสำหรับรอบพัฒนา

เริ่ม S01 ยืนยัน runtime ที่ใช้งานจริง สิทธิ์แหล่งข้อมูล และทะเบียนสถานี PCD จากนั้น S02 เติม fixture/field mapping จากผล probe ที่ทำแล้ว → S03 schema/local storage → S04 เริ่ม capture พยากรณ์จริง พร้อมเดิน pilot ERA5 และ PCD ใน S05–S06

หน้าวิเคราะห์แรกยังเป็นฝนใน S09 เพื่อพิสูจน์ probability 0–100% กับ rainfall bars และการเลือกเวลา/พื้นที่ร่วมกัน แต่เพิ่ม data contract และ history API จาก S08 ก่อน รายงานพยากรณ์ ย้อนหลัง และประเมินความแม่นยำใช้ snapshot กลาง และเปิดเฉพาะประเภทที่มีข้อมูลรองรับ

รายละเอียดผลส่งมอบ เกณฑ์ผ่าน dependency การหยุด/resume และ session handoff อยู่ใน [แผนฐานข้อมูลย้อนหลัง การเชื่อมต่อ และรายละเอียด 14 sessions](D:/MyWebApps/bkkair/docs/HISTORICAL_DATA_CONNECTION_SESSION_PLAN_TH.md)

รอบนี้ปรับเอกสารแผนและตรวจอ่านแหล่งข้อมูลตัวอย่างเท่านั้น ยังไม่ได้แก้โค้ดหน้าจอ สร้างฐานข้อมูลจริง เปิด scheduler ซื้อบริการ หรือ deploy

## 18. ขอบเขตข้อมูลย้อนหลังที่เพิ่ม

ฐานย้อนหลังและ ingestion อยู่ในแผนรอบนี้ แยกจากระบบบัญชี/ลิงก์รายงานถาวรที่ยังเป็นงานต่อยอด ผล probe ยืนยันการอ่าน ERA5, CAMS Global, GFS Previous Runs และ PCD CSV2024 ในขอบเขตตัวอย่างเท่านั้น

รายงานในหัวข้อ8รองรับสามประเภทเนื้อหา: พยากรณ์ปัจจุบัน, วิเคราะห์ย้อนหลัง และประเมินพยากรณ์ แต่ยังเลือกแบบย่อ/ละเอียดตามเดิม สัญญาข้อมูลหัวข้อ9ต้องเพิ่ม datasetClass, sourceProduct, valid interval, issued/modelRun/captured/ingested times, revision, QC และ coverage การจัดเก็บหัวข้อ10เพิ่ม raw assets/ingestion ledger และ history/runs/coverage API ก่อนส่งเข้าตัวเลือกกลาง

เป้าหมาย weather backfill แรกเสนอ2021–2025 โดยต้องตรวจ coverage; PM2.5 ตามปี/สถานีที่ตรวจได้จริง ข้อมูล reanalysis/แบบจำลองไม่ใช่ตรวจวัด และ historical stitched series ไม่ใช้แทนพยากรณ์รอบเดิม คลัง local forecast ต้องเริ่มเก็บผลจริงตั้งแต่ S04


## ส่วนขยายวันที่9กันยายน2026: ระบบเฝ้าระวังอากาศ
เพิ่ม [แผนระบบเฝ้าระวังอากาศ S15–S20](D:/MyWebApps/bkkair/docs/WEATHER_SURVEILLANCE_SYSTEM_PLAN_TH.md) เป็นขอบเขตต่อเนื่อง ครอบคลุมประกาศทางการ กฎเฝ้าระวังฝน/ความร้อน/PM2.5 สถานะข้อมูล วงจรเหตุการณ์ ศูนย์ติดตาม และการแจ้งเตือนที่ตรวจสอบย้อนหลังได้

| Session เพิ่ม | ผลส่งมอบหลัก |
|---|---|
| S15 | ทะเบียนกฎ เกณฑ์อ้างอิง แหล่งประกาศ freshness และ data eligibility |
| S16 | ฐานเหตุการณ์ evidence/revision/audit และ API contracts |
| S17 | ประเมินกฎ quality gate และ replay โดยไม่ส่งแจ้งเตือนจริง |
| S18 | ศูนย์เฝ้าระวัง map/list/detail/timeline/รับทราบ และรายงาน |
| S19 | Shadow mode ตรวจคุณภาพสัญญาณและความพร้อมส่งแจ้งเตือน |
| S20 | เชื่อมช่องทางที่เลือก ทดสอบครบระบบ และเปิดเป็นขั้นพร้อม rollback |

S01–S02 เพิ่ม discovery แหล่งประกาศและนิยามช่วงเฉลี่ย; S03 เตรียม identities/provenance; S04 เก็บพยากรณ์จริง; S08 ส่ง coverage/quality ให้ evaluator; S12 เพิ่มรายงานเฝ้าระวังเมื่อ S18 พร้อม S14 เปิดได้เฉพาะขอบเขตเดิม ส่วนแจ้งเตือนเฝ้าระวังภายนอกรอ S19–S20 ผ่าน

S15 เริ่มหลัง S02 ได้ ไม่ต้องรอ14sessionsจบทั้งหมด และไม่ต้องรอ backfill ห้าปีเพื่อเริ่มกฎที่ข้อมูลพร้อม งานเฝ้าระวังเพิ่มนี้ยังเป็นแผน ไม่ได้ตั้ง scheduler หรือส่งข้อความจริง รายงานอัตโนมัติ/บัญชีทั่วไปที่เคยไม่รวมยังไม่ขยายทั้งระบบ แต่สิทธิ์รับทราบ/แก้กฎและ preferences ที่จำเป็นต่อเฝ้าระวังรวมอยู่ใน S16/S20
